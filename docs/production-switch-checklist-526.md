## 3. 部署命令

> 手动触发生产部署流水线（`deploy-prod.yml`，`workflow_dispatch`）。push master 不再自动上线。

```bash
gh workflow run deploy-prod.yml --ref master -f ref=<SHA>
```

- `<SHA>` 填本次目标完整 40 位提交（候选 `93914c58c36da7f7b19c076b81b4395ad0e9d69f`；届时以 master 最新已过 CI SHA 为准）。
- **pre-flight 校验**（流水线内自动执行，任一不过即拒绝部署）：
  1. ref 解析为确定 SHA（只接受 master / 40 位 SHA / tag 名，拒绝任意分支名与 ref 表达式）；
  2. 该 SHA 必须落在 master 历史内（compare = identical / behind；分叉或领先 master 拒绝）；
  3. 该 SHA 在 `deploy.yml` 有成功的 CI 运行记录。
- 流水线内顺序：解析 SHA → 校验 CI → checkout → 生成 `.env`（Secrets 中转）→ 服务器探测与拉取预检 → 打包 / 传输 bundle 兜底 → 服务器拉代码、备份快照、构建重启 → 就绪检查 → RLS 自检。
- 部署期间关注流水线日志：predeploy 快照成功、容器起来、就绪检查 30 次内通过；失败按日志归因，不手工跳过闸门。

## 5. 回滚方案

### 5.1 代码回滚

- 用同一条生产流水线重新 dispatch 上一稳定版本：

  ```bash
  gh workflow run deploy-prod.yml --ref master -f ref=f219839b6c09940cf160d50a921658e90e8766e3
  ```

- 旧 SHA 必须在 master 历史内（`f219839` 为现状基线，pre-flight 可通过）；回滚部署同样走 CI 成功记录校验与 predeploy 快照。

### 5.2 数据回滚边界

- 本次新增 `tenant_module`、`tenant_module_audit` 两张表对旧版本**无害**：旧代码不读取这两张表，回滚到 `f219839` 后旧链路按原口径运行，不依赖删表。
- 回滚代码**不自动回退**模块授权行与审计行；如回滚后需要撤销某次授权变更，在后台把开关改回 off，或在授权窗口用回填脚本 `--revert` 删除目标校授权行（见运维手册 §3）。
- 作答、课堂、用户、录音等业务数据本次未做任何结构变更，不在回滚边界内；Alembic downgrade 仅作为异常时的最后手段，会摘除两张新表并丢弃其回填数据，不影响业务作答数据。
