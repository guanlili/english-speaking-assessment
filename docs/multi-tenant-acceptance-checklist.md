## 四、AC-05 真库受限角色探针（2026-11-16）

单测跑在 `app_test`（受限角色、四类断言齐备），但「真库真角色」一直没跑。本次在开发栈的 `app` 库上补做，用与生产同构的临时角色 `rls_probe_app`（`NOSUPERUSER NOBYPASSRLS` + schema/表授权），跑完即删角色与探针数据，期间零残留（`select count(*) from classroom where code like 'probe%'` = 0）。

| # | 探针 | 结果 |
| --- | --- | --- |
| 1 | 角色属性 | `rolsuper=f`、`rolbypassrls=f` |
| 2 | 无租户上下文 SELECT `classroom` | 0 行（策略 `coalesce(current_setting('app.tenant_id',true),'')=tenant_id::text` 生效） |
| 3 | 无上下文 INSERT | 被拒：`new row violates row-level security policy` |
| 4 | 上下文=默认学校 | 9 行，且 `count(distinct tenant_id)=1` |
| 5 | 同一连接切到第二校（默认校无该班） | 0 行，不串校 |
| 6 | 上下文=默认校却写第二校 | 被拒（WITH CHECK） |
| 7 | 清空上下文后复读 | 0 行，连接复用不残留 |
| 8 | 第二校上下文读 classroom（该校有 1 个探针班） | 1 行，`count(distinct tenant_id)=1` |
| 9 | 切回默认校读 | 9 行，探针班 0 行可见 |

**两点发现（写进验收说明，避免误解）**：

1. **身份层表不启 RLS**：`user`、`tenant` 不在 `RLS_TABLES` 里。以第二校上下文读 `"user"` 仍返回 15 行 / 4 个租户——这是设计如此（身份层靠应用层过滤，平台口径需要跨校身份），**不是漏洞**，但对外解释 AC-05 时必须说清「RLS 覆盖 32 张业务表，不含身份表」，否则会被误读成隔离失效。
2. **本地曾长期以超管连库（2026-11-16 已修正）**：`.env` 的 `APP_POSTGRES_USER/PASSWORD`、`PLATFORM_POSTGRES_USER/PASSWORD` 原为空，后端以 `postgres`（BYPASSRLS）连接，本地跑应用**绕过 RLS**——跨校越权在本地测不出来。2026-11-16 已按生产同构补齐并 `docker compose up -d prestart` 建角色（`ensure_db_roles.py`），复验：`GET /api/v1/classes` 返回 9 条（默认校），而 `classroom` 全表 10 条（另一校 1 条被 RLS 过滤），确认本地已在真实隔离下运行。留空 .env 仍会回落超管，重建环境后需重跑 prestart。

### 4.1 部署自检（2026-11-17 起）

`scripts/prod-rls-selfcheck.sh` 由 `deploy.yml` 在「服务器拉代码并重启服务」之后自动执行，把生产隔离状态写成 CI 日志：

| 判据 | 失败含义 |
| --- | --- |
| APP 角色 `rolsuper=0` / `rolbypassrls=0` | 受限角色被改成超管，RLS 形同虚设 |
| PLATFORM 角色 `rolbypassrls=1` | 平台通道失去跨校能力 |
| 业务表 `relforcerowsecurity` > 0 | 策略对表 owner 不生效，迁移可能被回退 |
| 受限角色缺上下文读 `classroom` = 0 行 | 策略没挂上或 `app.tenant_id` 语义变了 |
| 无 owner 身份的业务连接 | 应用没切到受限角色（回落 owner） |

本地实跑（2026-11-17，开发栈）：5 条全过；把 `APP_POSTGRES_USER` 改成 `postgres` 后 2 条转红、退出码 1，证明判据不是空转。

**生产实跑（2026-11-16 部署 run 43911230898，第一次带自检的部署）**：

| 判据 | 生产结果 |
| --- | --- |
| APP 角色属性 | ✔ NOSUPERUSER + NOBYPASSRLS |
| PLATFORM 角色属性 | ✔ BYPASSRLS |
| FORCE RLS 覆盖 | ✔ 32 张表 |
| 缺上下文读 classroom | ✔ 0 行 |
| 上下文内可见（默认校） | 22 行（仅提示，不判失败） |
| 业务连接身份 | ✔ 无 owner 连接 |

结论：**生产 RLS 不是"配置上应该有"，而是每次部署都会被验证的事实**。日志位置：该 run 的「部署到服务器 → 生产 RLS 自检」步骤。

### 实测顺带发现的限流问题（2026-11-18 已修复）

原实现：`app/api/routes/login.py` 两个桶——`ip:<client_ip>` 与 `user:<account>`，各 10 次 / 5 分钟。两个问题：

1. **同号不同校共享失败预算**：A 校 `s10001` 输错 10 次，B 校同名学号也被挡（两校同名学号是常态）
2. **一个班被另一个班的错误连坐**：学校机房普遍 NAT 单出口，10 次额度是「一个人能被试几次」的口径，按「一整个出口」计数必然误伤

现在改成三桶（额度按用途区分）：

| 桶 | 键 | 额度 | 作用 |
| --- | --- | --- | --- |
| 账号 | `acct:<school│->:<account>` | 10 / 5min | 防针对单账号爆破；**学校维度隔离**，两校同名学号互不影响 |
| 同校出口 | `ip:<school│->:<ip>` | 30 / 5min | NAT 出口共享；额度按「一个班各自试几次」给 |
| 全局出口 | `ipall:<ip>` | 60 / 5min | 跨校喷洒的兜底——放宽不等于放开 |

实测（开发栈，同一出口）：同校 30 个不同账号错密码全部 `400`、第 31 个 `429`；单账号第 11 次 `429`；两校同名学号失败预算互相独立（`tests/test_login_rate_limit_buckets.py` 四个用例固化）。

仍未改的口径：`/recover-password` 的 IP 桶依旧是 10 次 / 5 分钟（无学校上下文，且要防邮件轰炸）——批量开校或整班重置密码时错峰操作。
