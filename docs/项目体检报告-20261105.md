# 项目体检报告（2026-11-05）

审查范围：代码静态扫描 + 生产运行时数据 + 依赖/测试/运维链路。上一轮刚落地 CSP 与登录态 24 小时，
本轮不做重复审查，聚焦尚未系统检查过的面：存储增长、备份、监控、性能、可维护性。

## 结论

安全与代码质量的实际水平明显高于常见项目：认证、多租户隔离、注入防护、限流、幂等、测试覆盖
都已到位，且是**有机制**的（CI 每周依赖审计、RLS 强制、幂等键、审计日志）。

问题集中在**运维与数据生命周期**，不在业务代码：

- 学生录音永久保留（`AUDIO_TTL_DAYS=0`），文件只增不减
- 每日全量备份把整份音频打包进 bundle，保留 14 天 → 磁盘占用随音频量**成倍放大**
- 备份只有本机同盘一份，机器或磁盘故障即全丢

按当前数据量还能撑，按业务增长走会在几周内从"没感觉"变成"磁盘满、全站挂"。

## 一、必须处理

### 1. 录音无保留期限，磁盘与备份同时膨胀（最高）

现状：

| 指标 | 实际值 |
|---|---|
| `/app/audio` 体积 | 1.6 GB |
| 录音文件数 | 4850 |
| 单文件均值 | ~330 KB |
| `AUDIO_TTL_DAYS` | **0（不清理）** |
| 清理线程 | 已在跑（`main.py` lifespan 启动），但 TTL=0 时直接返回 |

推算（100 名学生、每人每天 5 次作答）：

- 音频日增 ≈ 500 × 330 KB ≈ 165 MB → 月增 ≈ 5 GB
- bundle 每天打一份 `audio.tar.gz` 全量快照，保留 14 天
- 稳态备份占用 ≈ 14 × 音频总量 → 音频到 60 GB 时，备份需要 840 GB

即：**磁盘 118 GB，音频 60 GB 就是硬上限，而按上面增速一年就到**。

处理建议（需产品确认保留期）：

```bash
# 生产 .env 追加（示例 180 天，按学校要求调整）
AUDIO_TTL_DAYS=180
```

代码侧无需改动，清理线程已实现终态作答 + 超期 + 未清理三条件，且会写 `audio_purged_at` 留痕。
配套需要跟学校说明"历史录音超过 N 天不可回放，评分结果不受影响"。

### 2. 备份只有本机一份，无异地副本

现状：`scripts/backup-local.sh` 产出 `database.sql.gz + audio.tar.gz + config.env + manifest`，
落在 `/opt/speakup/backups`，与数据库、应用**同一块磁盘**。磁盘故障、误删、服务器回收 = 数据全丢。

同机另一个项目（yujee）已有 `pg-backup-cos.sh` 上传腾讯云 COS，凭据和模式可直接复用。

建议最低动作：每日 bundle 完成后异步上传 COS，只保留最近 7 天，本地保留 3~5 个。

### 3. 备份保留策略与音频增长不匹配

现状：`find ... -name 'bundle-*' -mtime +14 -exec rm -rf` —— 逻辑本身正确（只删完整的 bundle），
但"14 天 × 每天全量"在音频增长后是自伤。

建议改为分层：

- 最近 3 天：每日一份（应对误操作）
- 每周一：保留 4 份（应对慢发现的问题）
- 数据库单备份（`pg_dump` 很小，可以保留 30 天）
- 音频从 bundle 里**移出**，只在每周那份里保留，或走独立对象存储

**踩到的坑（写后续 worker 测试要注意）**：测试文件顶层写 `from app.core.db import platform_engine` 会在收集阶段把引擎固化为默认（开发/生产）库，而 worker 函数内部是延迟 import、能拿到测试库覆盖值，两边不是同一个库，表现为"函数调用成功但断言读不到变化"。正确做法是在 helper/函数内延迟取引擎（`_engine()`），或统一在 conftest 里覆盖平台通道。

## 六、models.py 拆分（同日继续）

`app/models.py`（3309 行 / 174 个类）拆成 `app/models/` 包，**对外接口零变化**——全仓库 189 个 `from app.models import X` 的引用名逐一校验可用。

| `models/admin.py` | 369 | 运营指标、成本、变更日志、导出 |
| `models/__init__.py` | 418 | 198 个名字的统一再导出 + `__all__` |

**怎么保证拆完没改行为**（三步验证，可复用）：

1. **表结构指纹**：拆分前后各导出一次 `SQLModel.metadata`（38 张表的列类型/可空/默认值/外键/索引/唯一约束）→ 归一化掉对象内存地址后逐字节 diff，**完全一致**。
2. **导入面校验**：解析原文件顶层名 + 全仓库 AST 里的 `from app.models import X`，用 `getattr(app.models, name)` 逐一验证 → 198 个原名全在、189 个被引用名全可用。
3. **回归**：`pytest -q` 933 passed / 2 skipped；`ty check` + `ruff check` + `ruff format --check` 全绿。

**拆分时踩到的耦合点**（说明这几个类不该乱放）：

- `DashboardClassroomRow` 名字像课堂、实际被 `admin.py` 的看板聚合引用 → 归 admin，classroom 侧持有定义会形成反序依赖。
- `VOCAB_LEVEL_ORDER` 同时被 `content.py`（单元难度校验）和 `vocabulary.py` 引用 → 上移到 `base.py`，否则内容域反向依赖词库域。
- `learning.py` 的展示模型引用 `ExamItemSettings`、`ScenarioQuestionPublic`、`SentenceFramePublic`、`ClassroomExercisePublic` → learning 单向依赖 content/classroom，导入顺序必须是 base → core → content → classroom → learning → vocabulary → admin。
- 旧单文件靠 `from sqlmodel import Field, SQLModel` 的副作用让 `from app.models import SQLModel` 可用（`alembic/env.py` 与一个测试就这么写）→ `__init__` 里保留该再导出，避免为重构改迁移环境。
