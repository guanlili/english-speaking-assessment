# GitHub 项目管理试点

试点起点：2026-11-01。研发记录沿用本仓库；项目视图：https://github.com/users/guanlili/projects/3 。

## 一次工作的记录链

需求/缺陷 Issue → 一个或多个 PR → 验证 → 发布记录 → 验收证据。
每项业务任务保留一个主 Issue。小修可直接用 PR，但必须写明原因、范围和验证。
PR 使用 Refs #N；只有该 Issue 的全部研发验收标准均完成时才使用 Closes #N，阶段 PR 不关闭父需求。
代码合并不代表上线，部署成功不代表客户验收。记录状态时必须附来源及核验日期。

## 信息权威与旧试验衔接

- 本仓库：研发 Issue、PR、技术决策、测试与版本记录。
- 私有 Projects 字段：内部分类、预计人时、实际人时、交付状态；客户关系和商务信息只在确认可见范围后记录。
- 本仓库公开：不得把合同、报价、客户私人联系信息、人员工时明细或私有看板内容复制到公开正文。
- #222 规定的 Notion 双轨试运行仍有效；本试点新增研发追踪约定，不自动替换已有需求依据，不宣称已完成双向同步。发生内容冲突时记录差异并请负责人定稿。
- 需求修改保留原始来源、确认人/日期及变更原因。未确认的建议不得变成已承诺范围。

## 最小字段

| 字段 | 口径 |
| --- | --- |
| Title / Assignees | 任务与人工负责人；AI 执行者在 PR 中注明，不伪造 GitHub 账号 |
| Status | Todo / In Progress / Done 表示研发状态；空值表示待梳理，不能猜填 |
| 工作类型 | 功能 / 缺陷 / 客户变更 / 工程维护 / 管理 |
| 预计人时 | 人工投入估算，原估算与调整原因写在私有记录 |
| 实际人时 | 经本人确认的人工投入；空白=未记录，0=已确认零投入 |
| 交付状态 | 待核验 / 待发布 / 已发布 / 已验收 / 不适用 |

人时按小时；人日换算须先确定一天小时数。AI 运行时长、token 成本、人工投入、对客计费分别记录。
禁止以提交数、代码行数或 AI 墙钟时长推算人工工时。AI 无法核实的实际人时留空。
父需求用于汇总，工时只记在叶子工作项；若只有父 Issue，则阶段投入记为不重叠的明细，不能再给 PR 重复计费。
不同时把父项估算和已拆分子项估算纳入总和。改口径或估算时保留历史依据。

## AI 每次执行

1. 读 AGENTS.md、CLAUDE.md、AI_RULES.md 和相关模块说明；定位主 Issue，读正文及最新评论，注明采用的需求版本。
2. 查已有任务，避免重复建单；明确目标、验收、范围外、依赖及人工负责人。
3. 实现前澄清会影响范围/计费/数据安全的未决事项；不把管理试点视为新功能开发授权。
4. 按 PR 模板回填改动、验证、未完成项；只有实际执行的检查才写通过。
5. 结束时给出可复制的项目字段更新摘要；有 Projects 写权限时直接更新并复读核验，无权限则明确列出未回填字段。
6. 实际人时由人工确认；没有上线/客户确认凭证则保持待核验。内部字段不写进公开 PR。
7. 更新现有记录优先于新建平行台账；AI 对话不作为唯一交付记录。

## 历史迁移与试验验收

初始关联 #222–#232 与多租户相关 PR #233–#239，均以当前实际记录为准。

历史未知工时保持空白；评论中的部署结论标为“已有记录报告”，未经重新检查不得宣称本次已核验生产。
不批量补造历史需求，不提前创建 Release 或确认客户验收。

- 每次修改能追溯到需求或明确的修复原因；
- 每个 PR 有改动说明和真实验证结果；
- 人工投入能记录、能解释归因，未知值不变成 0；
- 能区分研发完成、已部署与已验收；
- 换 AI/开发者能从 GitHub 找到上下文。
