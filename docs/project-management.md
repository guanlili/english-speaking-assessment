# GitHub 项目管理试点

试点起点：2026-11-01。研发记录沿用本仓库；项目视图：https://github.com/users/guanlili/projects/3 。

## 一次工作的记录链

需求/缺陷 Issue → 一个或多个 PR → 验证 → 发布记录 → 验收证据。
每项业务任务保留一个主 Issue。小修可直接用 PR，但必须写明原因、范围和验证。
PR 使用 Refs #N；只有该 Issue 的全部研发验收标准均完成时才使用 Closes #N，阶段 PR 不关闭父需求。
代码合并不代表上线，部署成功不代表客户验收。记录状态时必须附来源及核验日期。

### 追溯链必须指向 Issue，不是 PR

`Refs #N` / `Closes #N` 里的 `N` 必须是 **Issue**。GitHub 的 Issue 与 PR 共用同一套编号空间，PR 也占号，所以 `Refs #18` 完全可能指向一个 PR：语法合法、不报错、也不会自动建立关联，只是追溯链在那一刻就断了。半年后有人沿着 `Refs` 想读需求背景，落到的是一个毫不相干的代码改动。

**自查**：打开 `https://github.com/guanlili/english-speaking-assessment/issues/<N>`。页面标题出现 `· Pull Request #N`、或标题行带 `pull request` 标签，说明它是 PR 而不是 Issue。

**这次的真实代价（2026-11-11 至 11-12）**：`#394`–`#404` 连续 11 个 PR 的关联需求段都写着 `Refs #16`/`Refs #18`/`Refs #19`，而这几个编号实际都是更早的 PR。根因是那批 `vocabulary` 拆分 PR 共用一份正文模板，错误被一路复制继承，且没有任何机器检查会发现它——CI 全绿、合并正常、只是记录无声地失效。

**处理与约定**：11 个 PR 已改为中性描述并注明原因。这批工作确实没有对应的需求 Issue，因此正确做法是写「工程维护（<具体类别>）」这类可验证的描述，**不虚构关联，也不留一个指向错误意图的裸 `Refs`**。

### 加一条 required check 要同步三处

分支保护（`PUT .../branches/master/protection` 的 `checks` 数组）、`deploy.yml` 里的 job 名、`required-checks-fallback.yml` 里的兜底 job 名，三者必须**逐字一致**。

原因是 `deploy.yml` 对 `**.md` / `docs/**` / `reviews/**` / `prototypes/**` / `gui-test-screenshots/**` 走 `paths-ignore`，纯这些路径的 PR 上整轮 CI 根本不运行。GitHub 对**从未上报过**的 required check 按 pending 处理，不是通过——合并会被一直 blocked，而且没有任何报错，`mergeable_state` 只是显示 `blocked`。所以 fallback 必须替每一条 required check 准备同名 job 直接报成功。

例外的两条：`后端 pip-audit` / `前端 npm audit` 来自 `audit.yml`，它没有 `paths-ignore`，纯文档 PR 上照常运行，不需要兜底。

**2026-11-12 的实测代价**：分支保护升到 6 条时漏了 fallback 的 perf-guard，此后任何纯文档 PR 都无法合并。这个错误和上一节是同一类——改动在闸门侧，生效点却在另一个文件里，没有任何检查会把两者对起来。

## 信息权威与旧试验衔接

- 本仓库：研发 Issue、PR、技术决策、测试与版本记录。
- 私有 Projects 字段：`类型`、`来源`、`需求人`、`工时(h)`、`开始`、`结束` 六个（devledger 规范）；用户已确认本试点的客户归属、工作量和商务记录可以记录在当前公开仓库；仅填已确认的事实。
- 本仓库公开：本试点允许记录已确认的客户归属和工时。凭据、学生个人信息、客户私人联系方式及未经授权的原始合同不入库；尚未提供的商务信息保持待确认。
- #222 规定的 Notion 双轨试运行仍有效；本试点新增研发追踪约定，不自动替换已有需求依据，不宣称已完成双向同步。发生内容冲突时记录差异并请负责人定稿。
- 需求修改保留原始来源、确认人/日期及变更原因。未确认的建议不得变成已承诺范围。

## 最小字段

| 字段 | 口径 |
| --- | --- |
| Title / Assignees | 任务与人工负责人；AI 执行者在 PR 中注明，不伪造 GitHub 账号 |
| Status | Todo / In Progress / Done 表示研发状态；空值表示待梳理，不能猜填 |
| 类型 | 需求 / 缺陷 / 优化 / 交付线 / 文档（devledger 交付类型，取代早期「工作类型」） |
| 来源 | 甲方 / 内部（甲方=客户可感知的需求，内部=工程侧投入） |
| 需求人 | 甲方联系人姓名或称呼；内部条目留空 |
| 工时(h) | 经本人确认的人工投入（小时）；空白=未记录，0=已确认零投入 |
| 开始 / 结束 | 工作起止日期；历史条目取提出/完成日期，不代表实际排期 |

人时按小时；人日换算须先确定一天小时数。AI 运行时长、token 成本、人工投入、对客计费分别记录。
禁止以提交数、代码行数或 AI 墙钟时长推算人工工时。AI 无法核实的工时(h) 留空。
父需求用于汇总，工时只记在叶子工作项；若只有父 Issue，则阶段投入记为不重叠的明细，不能再给 PR 重复计费。
不同时把父项估算和已拆分子项估算纳入总和。改口径或估算时保留历史依据。

## AI 每次执行

1. 读 AGENTS.md、CLAUDE.md、AI_RULES.md 和相关模块说明；定位主 Issue，读正文及最新评论，注明采用的需求版本。
2. 查已有任务，避免重复建单；明确目标、验收、范围外、依赖及人工负责人。
3. 实现前澄清会影响范围/计费/数据安全的未决事项；不把管理试点视为新功能开发授权。
4. 按 PR 模板回填改动、验证、未完成项；只有实际执行的检查才写通过。写 `Refs`/`Closes` 前先确认目标编号是 Issue 而不是 PR（判据见上节）；没有对应 Issue 时写中性描述。
5. 结束时给出可复制的项目字段更新摘要；有 Projects 写权限时直接更新并复读核验，无权限则明确列出未回填字段。
6. `工时(h)` 由人工确认；上线/客户验收状态写进 Issue 评论，不再单独设「交付状态」字段。公开记录仅限用户允许披露的内容。
7. 更新现有记录优先于新建平行台账；AI 对话不作为唯一交付记录。
