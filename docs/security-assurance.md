# 平台安全保障方案 / Platform Security Assurance Plan

| 项 | 内容 |
|------|------|
| 文档名称 | Charcoal 开口说（英语口语学习平台）安全保障方案 |
| 编制人 | 李梨 |
| 版本 | V1.0（2026-10-29 修订） |
| 适用范围 | 平台生产环境（含 Web 前端、后端 API、数据库、音频存储、部署链路）及配套运维流程 |
| 读者 | 学校管理方、项目相关方、运维与开发团队 |

> 本文档说明平台当前已落地的安全保障措施、短期强化计划与中长期路线。文中"已落地"的各项均可对应到实际代码与配置，验收时可逐项核查。

---

## 1. 总体思路

1. 平台安全采用纵深防御：接入层、应用层、数据层、运维层四层各设独立防线，单点失守不导致整体失控。
2. 核心原则是"关键资产与关键逻辑不放在前端"：评分、计时、成绩结算、题库下发全部由服务端权威裁决，浏览器端只做展示，即使前端被完整分析也无法伪造成绩或提前获取未发布内容。
3. 稳定与安全一体保障：所有变更经自动化测试流水线放行，生产部署可秒级回滚，数据每日备份并定期演练恢复。
4. 措施分"已落地"与"规划中"如实陈述，不做超出现状的承诺。

## 2. 已落地的安全措施

### 2.1 账号与身份认证

1. 三级账号体系（管理员 / 教师 / 学生），权限判定每次请求查数据库实时校验，前端只做界面分流，伪造角色参数无效。
2. 登录态采用 JWT 令牌（HS256 签名），密钥仅存于服务端，不通往下发。
3. 令牌绑定密码哈希指纹：修改密码或管理员批量重置后，学生旧设备上的登录态立即失效，无需等待过期。
4. 密码使用 Argon2id 现代哈希算法存储，数据库泄露也无法还原明文密码。
5. 学生账号由学校统一导入（学号 + 初始密码），支持批量重置；开放注册默认关闭，外来人员无法自行注册进入。
6. 会话过期返回 401 由前端自动登出；权限不足返回 403 且不影响在线状态。两类错误严格区分，权限不足的访问一律在服务端拒绝。

### 2.2 传输与接入安全

1. 全站强制 HTTPS（TLS 1.2 / 1.3），网页的 HTTP 访问一律 301 跳转加密通道；仅为部署健康检查保留内部探测口，不承载任何业务流量、不接受登录与作答请求。
2. 启用 HSTS（一年有效期），浏览器记住后不再接受对该站点的明文连接，防降级与中间人劫持。
3. 安全响应头齐备：页面与接口防被第三方网站嵌入（防点击劫持）、X-Content-Type-Options 防内容类型嗅探、Referrer-Policy 控制引用泄露。
4. SSL 证书通过 DNS 验证方式自动签发与续期，避免人工续期遗漏导致服务中断。
5. 服务器仅对外暴露 HTTPS（443）等必要端口，数据库、内部服务端口不对公网开放。

### 2.3 接口防护与防爬取

1. 登录及敏感接口部署滑动窗口限流，IP 与账号双桶计数，暴力破解密码与批量撞库会触发限流拦截（返回 429 并要求等待），持续攻击被持续拒绝。
2. 限流设计考虑共享网络场景（学校机房同一出口 IP）：正常用户成功登录即清除失败计数，不误伤；攻击者交替"失败尝试 + 正常登录"也无法洗白计数。
3. 全部业务接口需携带有效令牌，无匿名数据面；课堂内容接口校验本班学生身份，跨班访问被拒绝。
4. 未公布的学习内容（测验词讲解、未发布题单）服务端直接拒绝下发，学生端无法提前获取答案。

### 2.4 业务防作弊（服务端权威）

1. 模考计时以服务器时间为准，客户端刷新、换设备、改本地时间均无法延长作答时间。
2. 每次练习与考试基于发布时的题目快照执行，教师修改题目不影响进行中的作答；课堂同步轮询接口仅返回版本摘要，不泄露题目内容。
3. 评分引擎（语音转写 + LLM 评分）全部在服务端与可信云服务之间完成，评分参数、评分规则不下发前端。
4. 作答状态轮询接口只返回阶段、剩余时间与已提交题号等最小信息，不重复下发完整题单，减少内容暴露面。

### 2.5 防反向工程与知识产权保护

1. 生产前端为压缩混淆后的构建产物，且不发布 Source Map 源码映射文件，第三方难以还原出可读源代码，分析成本高。
2. 核心算法资产（评分规则、词库数据、题库内容、提示词）全部在服务端，前端被完整分析也不触及上述资产。
3. 生产环境关闭 API 在线文档与接口架构文件（OpenAPI）的对外访问，避免接口全貌被匿名枚举侦察。
4. 题库与词库内容按班级发布范围授权下发：学生只能看到本人所在课堂已发布的内容，不提供全量导出接口；配合接口限流与鉴权，批量爬取的门槛与成本被显著抬高。
5. 词库等版权材料执行授权红线管理：未获授权的资料不进入生产环境。

### 2.6 数据保护与备份

1. 每日 03:30 自动全量备份，内容覆盖数据库（SQL 导出）、全部录音与内容音频、部署配置，附带 SHA-256 校验清单，任何一步失败即整体作废不发布半成品备份。
2. 备份保留 14 天滚动；备份文件仅服务器属主可读，不进代码仓库、不放可公开下载目录。
3. 录音文件设置保留期机制，到期自动清理音频本体（当前保留 180 天，可按学校要求调整），评分结果与学情数据仍在数据库中长期保留，兼顾学生隐私与教学追溯。
4. 批量导出（录音 ZIP、学情报表）生成一次性文件并设置有效期，过期自动回收；每次课堂导出全程审计留痕（发起人、时间、范围、结果），教师身份方可发起。
5. 运行日志不记录请求正文、密码、令牌与录音内容；每请求携带请求标识（X-Request-ID）用于故障定位，排查无需接触敏感数据。
6. 学生可见文案中不暴露内部技术细节；测试环境使用独立数据库，测试数据永不写入生产库。

### 2.7 供应链与代码工程安全

1. 代码托管于私有仓库，主分支保护策略生效：任何人（含管理员）不能绕过自动化检查直接推送。
2. 每次变更自动触发完整流水线：代码规范检查、后端测试、前端测试、端到端浏览器测试全部通过才允许合并部署。
3. 生产环境全部密钥（数据库密码、签名密钥、第三方 API 密钥）由部署流水线从加密 Secret 存储生成，不落仓库、不经人手、不在代码中出现；配置键清单有自动化一致性校验，防止配置项静默缺失。
4. 部署流水线使用最小权限令牌（只读），即使流水线凭据泄露也无法篡改代码。
5. 依赖组件由自动化机器人持续监控升级（Dependabot），已知漏洞依赖在窗口期内更新。
6. 部署脚本、备份脚本、回滚脚本本身纳入自动化回归检查，防止"事故当刻才发现脚本失效"。

## 3. 运维稳定性保障（已落地）

1. 服务容器化部署（Docker），应用、数据库、网关相互隔离，单组件异常不蔓延至整机。
2. 部署采用"推送即流水线"模式：合并主分支后自动完成构建、测试、发布，全程无人为手工操作环节，消除人为误操作这一最大不稳定源。
3. 双通道回滚：常规问题走代码回退（revert）重新部署；紧急故障执行预置回滚脚本，秒级切回上一个可用版本。
4. 关键外部调用（语音转写、评分、合成）全程记录调用结果与耗时日志，第三方服务异常可快速定位区分，避免"平台故障"与"上游故障"混淆拖延处置。
5. 运行指标按日快照落库（业务量、评分队列、运行时峰值），跨服务重启长期保留，无需外接系统即可回溯历史趋势；管理员大盘可视化呈现。
6. 后台清理任务（音频过期、孤儿文件回收）自动化执行并有幂等设计，长期运行磁盘不因垃圾文件增长而拖垮服务。
7. 变更影响控制：纯文档改动不触发部署重启，教学高峰期平台不会因非必要变更中断。

## 4. 短期强化计划（本季度内）

1. 异地备份：每日备份包加密上传至云端对象存储（与生产服务器物理隔离），消除"整机磁盘故障丢失全部本地备份"的单点风险；这是当前备份体系唯一的结构性短板。
2. 告警通道补齐：补全邮件告警凭据，使备份失败、成本异常等关键事件第一时间通知运维人员，替代人工巡检发现。
3. 恢复演练制度化：按既有隔离恢复流程每季度演练一次完整恢复（数据库 + 音频 + 配置），记录实际恢复耗时，确保备份"可用"而非仅"存在"。
4. 补充平台用户协议与版权声明页面，明确账号使用、内容版权与二次分发约束，为版权主张提供协议依据。
5. 密钥轮换规程：梳理签名密钥、数据库密码、第三方 API 密钥的定期轮换操作手册，纳入运维日历。
6. 安全基线复核：对服务器安全组规则、开放端口、系统账号做一次全面复核并留档。

## 5. 中长期安全路线（6–12 个月）

1. 云侧防护按需接入：评估接入 Web 应用防火墙（WAF）与 DDoS 流量清洗（涉及新增云服务费用，与学校确认后再实施；当前依赖接口限流与最小暴露面）。
2. 等级保护合规：如学校或教育监管有明确要求，配合完成等级保护 2.0 定级备案与测评（费用较高、周期较长，需与学校共同商定后启动）。
3. 安全检验常态化：日常以内部安全审计与自动化测试为主；如学校有要求，可引入第三方渗透测试，发现的问题按严重度排期修复（费用另计）。
4. 集中审计日志：管理员与教师的敏感操作（导出、重置、内容删除）落独立审计表，满足事后追责与内部审查需要。
5. 登录加固按需开发：如学校管理有要求，可为教师与管理员账号增加双因素认证或登录验证码（当前未启用，属按需开发项）。
6. 容灾架构评估：结合使用规模与成本，评估数据库高可用与跨可用区容灾方案，将数据灾难场景的服务恢复目标从"小时级（重灌备份）"向"分钟级"推进。
7. 未成年人个人信息保护专项：按《个人信息保护法》对不满十四周岁学生信息的特殊要求，完善告知同意流程与数据分类分级。

## 6. 应急响应与恢复目标

1. 故障分级响应：一般故障（单功能异常）当日修复发布；严重故障（平台不可用）立即执行回滚脚本恢复服务，再定位根因。
2. 数据恢复目标（现状承诺）：备份每日一次，极端情况下数据损失窗口最长 24 小时（RPO ≤ 24h）；完成异地备份后进一步消除整机风险。
3. 服务恢复目标：版本缺陷类故障秒级回滚恢复（RTO 分钟级）；数据灾难类故障按恢复演练实测时长为准，演练制度落实后向学校同步实测数据。
4. 每起故障产出书面复盘（时间线、根因、改进项），改进项进入开发排期跟踪闭环，持续降低同类故障复发概率。
5. 平台侧与学校建立联络机制：故障影响教学时第一时间通知任课教师，并提供替代教学建议。

## 7. 数据合规与隐私

1. 平台部署于境内云服务器（腾讯云），域名已完成 ICP 备案，数据不出境。
2. 收集的学生信息限于教学必需（姓名、学号、班级、作答与录音），不收集与教学无关的个人信息，遵循最小必要原则。
3. 学生录音仅用于口语评分与教师回放，不用于任何第三方用途，不与外部共享。
4. AI 评分调用境内合规云服务（火山方舟），语音数据仅做即时转写处理，不留存于第三方用于其模型训练（以服务协议为准）。
5. 数据删除与导出请求：学校提出的学生数据删除、班级整体导出需求，由管理员在平台内操作或运维执行，操作留痕。

## 8. 责任分工

1. 李梨：负责本方案的编制与持续维护，涵盖平台安全架构、账号与数据安全措施、合规路线，以及生产运维稳定、备份恢复演练、告警响应与应急处置。
2. 重大变更（新增对外承诺、安全事件后的措施调整）需同步更新版本号并通知学校方。
